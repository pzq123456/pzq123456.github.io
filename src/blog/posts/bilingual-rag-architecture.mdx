内部有一批测绘规范、项目报告和历史合同。它们大多是 PDF 和 Word，中英混排：同一份规范里中文条款旁边就是英文术语，扫描件还带着表格、页眉和盖章。传统关键词检索面对"这份项目的沉降观测精度要求是什么"这类问题时，经常要么搜不到，要么返回一堆名字相似但内容无关的旧文件。

这就是这套双语 RAG 的起点。它不是平台上的一个配置项，而是我们用 **Python + Docker** 从零搭起来的服务：一台 4 × NVIDIA L20 的机器，上面跑着 TEI 向量服务、FastAPI Agent 网关和 Qdrant；文档从 Docling 进来，答案带着出处和置信度出去。

写这篇时我读了一篇做游戏策划知识库的 RAG 复盘。领域完全不同（游戏设计 vs 测绘），依托平台也不同（他们是托管平台，我们是自己的 GPU 服务器），但拆开看，两边的骨架几乎一样：**摄入切分 → 混合索引 → 查询生成**，每一层都在做同一组取舍。这种"大差不差"的感觉挺有意思——它说明 RAG 的工程问题已经相当收敛了。所以我借的只是"按层拆、把取舍写在图上"这个讲法，下面的系统、实现和坑，全部来自我们这个项目。

## 先看全景：三层，八个节点

<RagArchitectureDemo />

图上的三条带子就是三个层：

- **L1 摄入与切分**：文档 → 清洗 → 切块。取舍是"增量同步与双路径切分 vs. 延迟"。
- **L2 混合索引与检索**：向量化 → 存储。取舍是"Dense + Sparse 与自托管 GPU vs. 成本"。
- **L3 查询、重排与生成**：改写 → Agent → 答案。取舍是"精排与引用 vs. 端到端延迟"。

把节点画出来之后，一个很直观的感受是：真正决定效果的往往不是模型有多新，而是每个箭头之间有没有把上下文丢掉。下面逐层说。

## L1：让文档"可检索"，而不是"被塞进向量库"

### 先转成保留结构的 Markdown

第一步是把企业内部数千份 PDF / Word 清洗成 Markdown。这里的关键不是"转成纯文本"，而是**保留标题层级**。测绘规范里的编号条款——比如 `4.2.3 沉降观测`——本身就是极强的检索信号：它既是语义边界，也是日后引用的锚点。如果转换时把标题拍平，后面再想恢复就很难了。

我们用 Docling 做这一步。它会尽量还原标题、表格和阅读顺序，输出的是带层级的 Markdown，而不是一坨字符串。

### 双边界切分：结构 + 语义

参考实现里有一条很清晰的分流：有标题层级的文档走"标题敏感切分"，没有的走语义切分 API。我们的做法接近，但放在一个组件里完成——HybridChunker 同时考虑两种边界：

- **结构边界**：标题、编号条款、表格边界优先切；
- **语义边界**：对没有清晰标题的报告段落，按语义相似度找断点，而不是固定窗口长度。

固定长度切分最大的问题是会把一个完整判定切成两半，或者把两段无关内容拼在一起。双边界的目的就是让每个 chunk 自己能站得住。

```python title="ingest.py"
doc = DoclingConverter().convert(path)          # PDF / Word -> Markdown（保留层级）
chunks = HybridChunker(
    structural_boundary=True,                   # 标题 / 编号条款
    semantic_boundary=True,                     # 无结构段落按语义断点
).chunk(doc)
for chunk in chunks:
    chunk.id = deterministic_id(path, chunk.heading_path, chunk.index)
    qdrant.upsert(collection="survey_kb", points=[chunk.to_point()])
```

### 幂等写入比"写入"更重要

这是托管平台不会替你操心、但自建系统一定会踩的坑：流水线重跑一次，chunk 不能翻倍。我们用 `(文档路径, 标题路径, 块序号)` 生成确定性 ID，再用 `upsert` 写入 Qdrant——重复处理同一份文档只会覆盖，不会产生副本。

参考实现用 `modifyTime` 做增量更新识别，比我们精细。我们目前走的是更朴素但安全的路线：**先保证每次写入都可以安全重复**，再考虑"只写变化的部分"。对小规模内部知识库来说，这个取舍很划算。

## L2：Dense + Sparse，以及自己养 GPU 的代价

### 为什么一个模型要两种表示

BGE-M3 的价值在于"一个模型，三种检索能力"。我们用到其中两种：

- **Dense 向量**：负责语义泛化。用户问"沉降观测的精度要求"，能召回讲"变形监测等级"的文档；
- **Sparse 向量**：负责精确命中。像 `GB 50026`、`RTK`、`CORS`、`1:500` 这类规范编号和缩写，在测绘语境里几乎携带了全部信息量。纯向量检索很容易把"某个具体的标准号"匹配成"一篇讲 GPS 的泛泛文档"。

参考实现报告过加入 BM25 后 Recall@5 提升 11.4%——那是他们的领域和评测集上的数字，不能直接搬到我们这里。但对"专业缩写 + 口语化提问"混合的场景，两种表示互补这个结论，我们自己的抽查也成立。

### TEI 独立部署：存算分离

我们把向量编码拆成独立服务：

```yaml title="docker-compose.yml"
services:
  tei:                                   # BGE-M3 向量推理，GPU 常驻
    image: ghcr.io/huggingface/text-embeddings-inference:1.6   # GPU 构建
    deploy:
      resources:
        reservations:
          devices: [{ capabilities: [gpu], count: 4 }]
  agent:                                 # 无状态 FastAPI + Pydantic AI 网关
    build: .
    depends_on: [tei, qdrant]
  qdrant:                                # 有状态：持久化卷 + 快照恢复
    volumes: ["qdrant_data:/qdrant/storage"]
```

这样切分的好处是：编码、检索、生成可以各自扩缩容。TEI 挂掉只影响入库和新查询的编码，已经写进 Qdrant 的数据仍可检索；Qdrant 用持久化卷加快照恢复，重建服务不会丢索引。

参考实现直接调用平台托管的 `public-bge-m3`，零运维，但按量付费、模型版本受平台约束。我们则在 4 × L20 上自己跑 TEI：没有调用费用和平台锁定，代价是要自己容量规划、盯模型版本、处理 GPU 服务的故障恢复。**这是整套系统里我们和托管平台路线差别最大的一层**，也是"心路历程"最不一样的地方——很多在平台上只是一个开关的东西，在这里变成了一行 docker-compose 配置和一个监控项。

## L3：查询侧才是"双语"真正发生的地方

### 中英双语 Query 改写

我们的语料本身就是中英混排的，而用户的提问语言并不决定答案出自哪种语言。所以检索前会让 Qwen Agent 针对每个问题生成**至少两组中英双语 Query**，例如：

```text title="query-rewrite 示例"
输入：沉降观测的精度要求是什么

输出：
1. 沉降观测 精度要求 GB 50026 变形监测
2. settlement observation accuracy requirement level
3. 二等沉降观测 精度 限差
```

并发召回 Qdrant 的 Top-K 切片后按 ID 去重，再强制要求回答带原文溯源与置信度。这一步比"把用户原话直接编码成向量"稳健得多——尤其是用户用中文提问、但最权威的那段规范恰好是英文时。

参考实现做了意图识别、多轮 Query 重写和多 Query 分解三层预处理，比我们细。我们目前集中在"双语改写 + 并发召回"这一件事上，因为我们的痛点主要是语种鸿沟，而不是多轮指代或多意图路由。

### 精排：同样的位置，不同的分量

架构图把"多路召回 + 精排"画在 Agent 节点里，是因为它们解决的是同一个问题：召回负责不漏，精排负责排对。

参考实现用 Cross-Encoder（bge-reranker-v2-m3）做精排，并给出了很扎实的消融数据。我们这一层目前更克制：以 ID 去重和相似度排序为主，Cross-Encoder 仍在评估中。原因很实际——同一台 4 × L20 还要同时承担 embedding 和生成，延迟预算必须留出来。图上那条 "Cross-encoder rerank & citations vs. end-to-end latency" 的取舍，对我们不是理论问题，而是每天要不要多加一个 GPU 服务的工程决策。

### 答案：可溯源，也要知道边界

最后一步用的是 Pydantic AI。相比纯 Prompt 约束，强类型输出有个明显好处：**溯源和置信度是必填字段，不是模型想不想写的问题**。回答里必须带原文出处，信息不足时明确说明，而不是一本正经地编。

```python title="agent.py"
class Answer(BaseModel):
    text: str
    sources: list[SourceRef]      # 必填：原文出处
    confidence: float            # 必填：置信度
```

我们没有做同等规模的离线评测，所以这里不引用任何外部数字——它们说明不了这套系统真实的效果。

## 还没做完的事

- 建一套正式评测集（几十条量级），用 RAGAS 跑 Faithfulness / Answer Relevance，而不是靠人工抽查；
- 做 Cross-Encoder 精排的收益—延迟曲线，再决定要不要为它单独留一张卡；
- 父子树块：命中子块时把父块上下文一起交给生成，缓解"断章取义"；
- 测绘术语同义词表：`RTK` ↔ 实时动态定位、`CORS` ↔ 连续运行参考站；
- 从"重复写安全"走到"只写变化的部分"，做真正的增量同步。

## 结语

RAG 的难点从来不是把向量塞进数据库，而是在每一个箭头上想清楚：这里会丢什么，丢得起吗。架构图上那三条 trade-off，没有一条是设计出来的，都是被真实问题逼出来的。

下次有人问我"你们和某某大平台的 RAG 有什么不一样"，我想答案不是某个组件的有无，而是：他们把复杂度收进了平台，我们把复杂度摊在了自己的 Python 和 Docker 里——然后一层一层，把它讲清楚。
