一个 Agent 在演示环境中能完成退款排查，上线数周后却开始混淆历史数据与当前状态：把已关闭的旧账当成今天的异常，把测试环境的记录算进生产报表，对同一客户给出互相矛盾的结论。代码、提示词和模型版本都没有变化。

这类问题通常无法靠更换基座模型解决。大模型本身是概率系统，仅靠提示词中的口头约束，很难让它在长周期、多工具、跨会话的运行中保持稳定。过去两年，一线团队在生产环境中逐步补出的是一组确定性护栏：限定决策权、管理上下文、约束工具接口、维护结构化记忆、控制多智能体的协作成本，以及用评测和监控验证每一次改动。

下面六个部分按这条链路展开，重点放在机制与取舍上：每种做法解决什么问题、代价是什么、什么情况下不该用。

---

把六个部分串起来看，Agent 工程的重心并不在模型侧，而在模型周围的那层系统。工作流划定了决策权的边界，上下文工程决定模型每次能看到什么，工具设计约束它与外部系统的交互方式，记忆系统承载跨会话的状态，多智能体只在收益大于协调成本时才引入，评测与可观测性则让每次改动有据可依。

这些护栏的共同点，是把不确定性收敛到可控范围：能由确定性代码完成的判断不交给模型，能在后台完成的处理不暴露给交互界面，能用测试验证的改动不依赖人工直觉。模型提供推理能力，工程负责让这种能力在真实业务里稳定复现。

## 第一关：决策权与工作流边界

一个智能体在业务系统里表现不稳定，往往不是缺少能力模块，而是系统没有界定哪些路径由代码决定、哪些交给模型判断。规划（Planning）、记忆（Memory）、工具调用（Tool Use）这套三段式刻画的是能力构成，而非可直接照搬的施工图纸：它要求系统能分解目标、保留状态、调用外部能力，却没有规定如何编排、何时停住、出错后由谁接管。映射到生产架构，有限上下文削弱长程推理，预设执行链遇到意外错误很难自行调整。

Anthropic 的切分更接近工程现实：工作流（Workflow）由预定义代码路径编排模型与工具，智能体（Agent）则由模型动态决定过程和工具的使用。判据只有一条——决策权留在代码里，还是转移到模型判断里。同样的模型与工具，放在固定路径上是工作流，交到模型手里就是智能体。多数场景从最简单的方案起步即可。

在允许模型参与决策的前提下，有几种可组合的模式，各自有明确的适用边界：

* **提示词串联（Prompt Chaining）**：把任务切成固定子步骤，步骤间插入校验关卡（gate）。适用于顺序确定、每步可检查的场景；需要按结果分支时，硬编码链条就会断裂。
* **路由分流（Routing）**：先对输入分类再分流。适用于输入差异大、类别目标不同的场景；一套提示词优化所有类别，对某一类的改进常伤害另一类。
* **并行化（Parallelization）**：分片（sectioning）拆开独立子任务，投票（voting）让多次判断收敛。适用于子任务无依赖或结果可由多数票裁定；硬拆串行依赖只会引入冲突与成本。
* **编排者-工人（Orchestrator-Workers）**：由中心模型现场分解并分发子任务。适用于子任务无法预列的场景；结构稳定时引入动态分解，只增加不确定性。
* **评审-优化（Evaluator-Optimizer）**：生成方与评审方循环迭代，直到满足评审标准。适用于标准明确、产出可判断的任务；标准模糊时循环无法收敛，只累积延迟。

让模型掌握决策权的代价需要单独评估。最显著的是错误复合：前一步的偏差被后一步当作事实放大，有状态的系统出错后通常无法从头重启，只能从中断处恢复。其次是延迟与成本——动态路径的推理轮次不可预测，一般先用最强模型建基线，再换小模型找平衡点。边界条件要在设计阶段明确：设置停止条件，把高风险执行放进沙箱，让环境返回的真实结果成为依据。

防御做成分层护栏（guardrails）：相关性、安全与个人信息（PII）过滤、内容审核、工具权限分级（区分读写、可逆性与资金风险）、规则校验、输出校验，逐层收窄风险面。更可行的方式是乐观推进，让校验与执行并发，触发时由拦截开关（tripwire）中止。人不必全程盯运行，只需在两个触发点接入：失败次数超过阈值，以及即将执行高风险且不可逆的动作。

传统对话由人发起、一次一个会话，扩展的是人的注意力，而非事件吞吐量。环境智能体（Ambient Agents）监听事件流并采取行动，可并行处理多个事件，但不等于完全自主。人在回路（HITL）留三个口子：通知（notify），只报告不行动；提问（question），信息不足时向人确认而非猜测；审核（review），危险动作要求审批，并允许编辑与反馈。三个接口既给高风险动作装了关卡，也把纠正积累成反馈信号。

把用户的判断收敛为工程结论：多数场景追求确定性交付，做法是把不确定性消化在后台，让对话退回处理异常的通道，而不是默认交互方式。代价是前端更薄、后端更厚——复杂度不会因界面简单而消失，只是被移到可评测、可回滚处。

## 第二关：上下文工程：把注意力当稀缺资源

随着上下文增长，模型对早期信息的回忆准确率会下降：一条明确写入提示词的约束，可能在几千个 token 之后不再被稳定遵循。这一现象被称为上下文腐烂（Context Rot）。原因是注意力预算（Attention Budget）有限，模型能分配给全部 token 的注意力总额存在上限。Transformer 的注意力计算量与序列长度呈 n² 关系；训练分布又以短序列为主，靠位置插值外推到更长窗口还会退化。因此性能随长度变化是一条平缓的斜坡，不存在突然断裂的临界点。

把上下文当作稀缺资源管理，对应上下文工程（Context Engineering）：每次推理时策划一组最小的高信号 token 集合。每放入一个 token，都会挤占其他 token 可分配的注意力。

在实践中，有几个关键的设计取舍：

* **系统提示词的颗粒度要适中**：一端是硬编码的 if-else 手册，规则未覆盖即失效；另一端是空泛口号，几乎不构成约束。更可行的是给出与目标匹配的明确规则，并用 Markdown 分节或 XML 标签让结构承载信号。精简不等于缩短，删掉必要约束是另一回事。
* **工具集保持最小可行**：人面对工具清单都难以判断该调哪个时，模型更难以选择。应优先移除职责相近的工具，控制语义重叠度。
* **示例讲究典型而非穷举**：少量、多样化、代表常规用法的 canonical（典型）示例，通常好于堆砌所有边界情况；后者既消耗 token，也容易让模型把边缘案例误认为常态。
* **预加载与即时加载取混合**：预加载提升确定性，但持续占用预算；即时加载（Just-in-Time）只把路径、查询、链接这类轻量标识符留在窗口中，细节运行时用工具取回。文件层级、命名与时间戳本身就是信号，不应抹平。更稳的做法是把高频规则前置进 `CLAUDE.md`，细节通过 `glob` / `grep` 按需检索，绕开过时索引；代价是延迟增加。

长周期运行的难点在于窗口之间如同换班工程师，后一班无法获知前一班的进展。工程上通常按任务形态选择三种手段。

* **压缩（Compaction）**：窗口接近容量时把历史改写成摘要，适合往返多、缺少明确里程碑的场景。先保证召回（recall），保留架构决策、未解决的错误与实现细节，再调整精确率（precision）；最安全的一步是清理陈旧的工具调用结果。
* **结构化笔记**：里程碑清晰的任务更适合让 Agent 自行维护 `NOTES.md` 或待办清单，对关键对象计数、绘制状态地图，把状态外化到文件。
* **跨窗口脚手架**：需要并行探索时，用 Initializer 与 Coding agent 分工。Initializer 先运行 `init.sh`、写出进度文件（progress file）与特性清单（每条带 `passes` 字段，初始为 false）、完成首次 git commit；Coding agent 此后每次只做一个特性，留下结构化更新并提交。会话开场有固定仪式：确认目录、读进度文件与特性清单、看 `git log`、跑 `init.sh`、执行端到端基础测试，再动手。清单用 JSON 比 Markdown 更难被改写，测试不允许删改，只更新 `passes` 字段。端到端验证通常需要显式要求，默认 Agent 只会写单测或用 `curl` 探活。

两处风险值得单独指出。压缩会漂移：反复摘要后摘要逐渐偏离原始事实，对策是保留原始记录及其链接。另一处是 clean state（干净状态），这里的“干净”指当前状态可以直接合并进 main；每个特性完成后提交一次 commit，既便于回退，也避免把半实现、无文档的工作留给下一个窗口。

## 第三关：工具设计与 ACI（Agent-Computer Interface）

把现有的后端 REST API 直接封装成 Tool Schema 交给 Agent，在生产环境中往往表现不佳。常见的问题是：参数类型或枚举值填错、调用不存在的接口，或者在检索失败后直接基于参数猜测生成结论。

根本原因在于调用契约发生了变化。传统微服务之间的 API 调用连接的是两个确定性系统，调用方严格遵循接口规范；而 Agent 工具调用连接的是一个具有概率性的推理模型，它可能忽略约束、误读字段语义，甚至在上下文过长时产生注意力偏差。因此，工具设计的本质不是暴露后端能力，而是为概率性调用者构建清晰的交互界面（ACI）。

在实践中，有几个关键的设计取舍：

* **提升业务内聚度，减少中间态流转**：不要把细粒度的 CRUD 接口原封不动地暴露给模型。例如，排查客户退款不需要模型先调用 `list_users` 拉取全量用户再自行遍历比对，而应提供 `search_customer_refunds(customer_name, order_id, status)` 这类聚合查询接口。将过滤、关联与聚合逻辑留在确定性代码中，可以显著减少不必要的上下文占用与推理步数。
* **控制返回载荷与字段语义**：工具返回应优先提供具备语义区分度的字段（如名称、状态、关键摘要），避免直接暴露无意义的内部 UUID 或冗余元数据；对于可能返回大量数据的接口，应支持 `concise` 与 `detailed` 等分级输出，并设置明确的 Token 上限（例如单次不超过 25,000 tokens），超限时返回分页或过滤指引，而不是直接撑爆上下文窗口。
* **通过参数约束实现防呆（Poka-yoke）**：与其在 System Prompt 中反复强调“必须使用绝对路径”，不如在工具参数校验层直接拒绝相对路径，并返回明确的重试指引。在 SWE-bench 等代码任务中，目录切换导致的路径错误往往可以通过收紧参数契约直接消除，这比依赖 Prompt 约束更稳定。
* **建立基于轨迹的迭代闭环**：工具描述的有效性不能仅靠静态评审判断。更可行的做法是使用真实的多步任务集驱动 Agent 运行，记录工具调用失败率、Token 消耗与任务耗时作为基线；结合完整执行轨迹（transcript）和模型在调用前的推理输出，定位工具描述中的歧义点并进行针对性修改。同时需保留独立的留出测试集（held-out set），避免针对特定评测集过度调优工具描述。

## 第四关：记忆系统的分层与生命周期管理

一个 Agent 在多轮交互或跨会话运行中出现“遗忘早期约束”或“混淆测试与生产数据”，通常不是基座模型能力不足，而是混淆了上下文窗口、对话历史与持久化记忆这三种不同层级的机制。

* **上下文窗口（Context Window）**：单次推理可用的 Token 预算，属于瞬态工作空间。随着长度增加，注意力会被稀释，且长序列推理成本更高。
* **对话历史（Chat History）**：按时间顺序追加的消息记录，是原始交互流水，本身不具备状态提炼、去重或冲突消解能力。
* **记忆系统（Memory）**：用于跨会话沉淀状态、事实与规则的结构化机制。

按时间跨度与职责，工程上通常将记忆拆分为四类，避免混用：

1. **Working Memory**：当前推理轮次实际参与计算的上下文内容，核心诉求是高信噪比与精简。
2. **Episodic Memory**：具体的历史事件与执行记录（如某次故障排查过程、某次变更记录），应保留原始依据与时间戳，以便追溯。
3. **Semantic Memory**：从历史经历中提炼出的稳定事实或领域知识，需要处理更新与冲突问题。
4. **Procedural Memory**：指导 Agent 行为的规范、流程与约束（如 `AGENTS.md` 或各类操作守则），具备明确的工程属性，适合纳入版本控制进行 Code Review 与回滚。

在架构选型上，目前主要有两类常见思路：

* **类虚拟内存机制（如 Letta / MemGPT）**：将核心记忆块常驻在上下文中供模型读写，同时将海量历史归档到外部检索存储，由模型通过工具按需分页调取。这种设计直观，但对记忆块的描述精度和常驻容量控制要求很高，否则容易挤占注意力预算或导致写入冲突。
* **数据管道与混合存储（如 Mem0 / LangGraph Store）**：在写入阶段完成信息抽取、结构化、去重与冲突解决，并结合向量检索、图/时序关系与结构化查询进行存储，同时区分线程内状态（Checkpointer）与跨线程长期记忆（Store）。在实际业务中，检索增强（RAG，回答“外部文档说了什么”）与长期记忆（回答“系统与用户上下文中沉淀了什么”）通常是互补的。

记忆写入可以放在**热路径**（实时写入，保证状态及时生效，但增加单次响应延迟与推理干扰）或**后台异步路径**（降低在线延迟，但存在一定的数据新鲜度滞后）。无论采用哪种方式，完整闭环都包含**写入、维护（manage）与读取**三步。只写不维护会导致记忆膨胀、旧规则覆盖失效以及过时事实引发误判；维护阶段引入版本号、时间戳、原始记录溯源以及定期清理机制，是保证记忆长期可用的关键。

## 第五关：多智能体协同的边界与成本

把任务拆给多个 Agent 并行处理，并不会自动提升吞吐。常见的情况是：子任务反复确认同一个前提、为同一份资料重复检索、各自更新共享状态又相互覆盖。收益被协调成本抵消，根因在于拆分没有改变信息边界，只是把单窗口内的冲突搬到了多窗口之间。

是否该拆，判断信号看的是工具语义重叠度，而不是数量。给一个 Agent 挂十几个职责清晰、边界分明的工具，它通常能稳定运行；换成不到十个语义高度重叠、谁都能接手的工具，它反而开始卡壳，因为模型从清单里挑不出该用哪个，人往往也挑不出。再往上，提示词里写满分支条件，if-else 不断膨胀；或者一个窗口要同时装下多路探索的中间态，根本放不下。到这一步才值得考虑拆分。

拓扑选择上，有两个常见取向：

* **中心化监督（Supervisor）**：把子 Agent 当成一只工具来调用，中心节点保留控制权与用户接口，子 Agent 只负责执行并回传结果，适合需要汇总与把关的并行任务。
* **交接（Handoff）**：没有唯一中心，控制权随对话转移给下一个 Agent，适合客服路由与对话分流。

二者一个重在调度，一个重在转交。与之正交的是分解方式：**固定分片（sectioning）**在代码里预先写死子任务，适合边界已知的场景；**动态分解（Orchestrator-Workers）**由主控在运行时判断拆几块、派给谁，适合子任务临场才浮现的开放式调研。

核心机制是把子 Agent 当作并行上下文压缩器。搜索本身是压缩：每个子 Agent 在自己的窗口里花上万 Token 探索，只回传 1-2k 的精炼摘要，主窗口因此只吸收高信号。效果有数据支撑：Opus 4 担任主控、Sonnet 4 担任子 Agent 时，内部调研评测（research eval）比单个 Opus 4 高 90.2%；BrowseComp 上 token 用量单独解释 80% 的方差，工具调用次数与模型选择合计解释 95%。代价同样明确：单 Agent 约消耗 4 倍于对话的 token，多 Agent 约 15 倍。因此只在任务价值高、并行度高、信息量超出单窗口时划算；强共享上下文、多依赖的编码任务不适合拆分，否则必要的信息流会被切断。

提示词层面，优先处理最关键的几条：

* **委派时交代边界**：写清目标、输出格式、可用工具与来源、任务范围；只给一句笼统指令，几个子 Agent 必然重复劳动。
* **按复杂度分配工作量**：简单任务 1 个 Agent 跑 3-10 次调用，比对类 2-4 个子 Agent，复杂任务才上 10 个以上。
* **先宽后窄**：先铺开检索，再收敛深挖。
* **基于轨迹改工具描述**：用 tool-testing Agent 跑几十次摸出工具描述的盲点，后续任务完成时间降 40%。
* **并行工具调用**：可带来约 90% 的提速。

落地难点在运行时。同步执行是瓶颈：主控派发后难以中途调整，子 Agent 之间也不能互通，一个慢节点会拖住全局，异步方案更强但更复杂。错误会跨窗口复合，崩溃后不能从头重启，需要从检查点（checkpoint）续跑，并把工具失败信息回传让它自适应，配合确定性重试。评测看的是终态（end-state evaluation），不逐步核对每一步；子 Agent 之间反复转述会失真，更稳妥的做法是让它们把完整产物写入文件，只回传一个轻量引用。

## 第六关：评测与可观测性

Agent 是概率系统，同一输入两次运行可能给出不同结果，传统软件依赖的断言难以直接成立。评测（Eval）要补的，正是这样一层可重复、可回归的测试基础设施。需要先明确一点：评分器本身也是一段软件，编码了对“正确做法”的假设，假设之外的最优解会被它误判。Opus 4.5 在 τ2-bench 的订机票任务中发现政策漏洞，用更优方式完成订票，却被预设脚本判为失败。评分器的可信度并非天然成立，它同样需要验证。

先把术语摊开。任务（task）是一道考题，粒度类似一条测试用例；试跑（trial）是执行一次，重复执行才有统计意义；评分器（grader）给单次试跑打分；执行轨迹（transcript）记录全过程而不只是答案；最终状态（outcome）是环境被改成了什么样，与路径无关。外围还有两套脚手架：评测脚手架（eval harness）投喂任务、执行试跑、调用评分器；被测助手脚手架（agent harness）是提示词、工具与编排逻辑的总和。被评测的其实是两者的组合——改一句提示词，在度量上等同于换模型，这一点在归因时经常被忽略。

评测集通常分两类，职责不同。能力评测（Capability Eval）通过率偏低，用于爬坡；回归评测（Regression Eval）通过率接近百分之百，用于守底线。当能力评测通过率持续上升、信号因评测饱和（eval saturation）而变弱，它便“毕业”为回归集；回归集一旦下滑，往往意味着某次改动引入了真实退化。两者不宜混用。

评分器没有通用最优解。代码断言（code-based）快、便宜、客观、可复现，代价是脆弱，路径稍变就可能误杀；模型打分（model-based）灵活，能捕捉细微差别，代价是不确定、成本高，需要人工标注持续校准；人工评审（human）是金标准，代价是慢、贵、难规模化。实践中通常混合使用：代码断言守住确定性部分，模型裁判处理开放任务，再以人工抽样校准。几条取舍反复出现：

* **评最终状态而非路径**：不要检查工具调用顺序是否符合预设脚本，否则政策漏洞式的更优解会被误杀；真正要度量的是环境最终状态。
* **给部分分**：二元通过会丢失信息，部分分能区分“接近成功”与“完全失败”，让爬坡有可观察的梯度。
* **为模型裁判（LLM judge）留退路**：无法判断时允许输出无法判定（Unknown），按维度独立打分，定期用人工标注校准，避免整体印象主导结果。

可靠性口径也要区分。pass@k 指 k 次中至少一次成功，随 k 上升；pass^k 指 k 次全成功，随 k 下降。单次成功率 75% 时，跑三次至少过一次几乎是必然，三次全过只有约 42%。可重试的流程按 pass@k 设目标；涉及资金或不可逆操作的流程应盯 pass^k，因为用户承受的是连续成功。

落地不必从大型基准测试（benchmark）开始，20-50 个真实失败案例通常足够起步。每条任务收录前需两位专家独立判定一致，并配标准解法（reference solution）；should 与 shouldn't 样例要平衡，否则模型只需学会“多做”或“少做”就能刷分。每次试跑运行在干净隔离的环境中——曾有 Agent 靠读取上一轮残留的 git history 作弊，分数虚高。评分之外还要读执行轨迹，许多失败模式藏在“没说出来的”决策里。CORE-Bench 上 Opus 4.5 从 42% 提升到 95%，靠的是修评分器、消除任务歧义与调整脚手架（scaffold），而非更换模型。把循环固化为评测驱动开发（eval-driven development）：每次改动先过评测，再谈上线。

离线评测只是一层防线。可观测性更接近瑞士奶酪模型（Swiss Cheese Model）：自动化评测、生产监控、A/B 测试、用户反馈、人工读执行轨迹、系统人工研究层层互补，每一层都有洞，叠起来才兜得住。前提是能留下完整的执行轨迹（trace）与环境最终状态，否则任一层事后都无法复盘。
